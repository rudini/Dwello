## C-1: Eine veraltete Sicherung legt die ganze App still

Der Healthcheck des Backends (docker-compose.prod.yml:125) prüft `r.ok`, und das Frontend wartet auf `service_healthy`. Ist die Sicherung `stale`, wird das Backend nach 3 × 30 s `unhealthy`, und Compose bricht den Start des Frontends ab («dependency failed to start: container dwello-backend is unhealthy»). Das verfehlt O1: «Die App zeigt einen Hinweis» und «sieht der Betreiber spätestens beim nächsten Öffnen der App» setzen eine laufende App voraus. Laut Issue bleibt das Backend nur dann unhealthy, wenn die Sicherung vor einer Migration scheitert; für eine veraltete Sicherung soll `/health` nur den Zustand melden. `docs/installation.md` nennt nur «the backend is `unhealthy`» und verschweigt, dass das Frontend dann nicht startet.

So lässt es sich zeigen: Einen Code bestätigen (Zeile in `backup_codes`, `confirmed_at` 25 h zurück), `./backups` auf dem Host mit `chmod 555` sperren, dann `docker compose -f docker-compose.prod.yml up -d --force-recreate`. Das Frontend startet nicht.

Mögliche Abhilfe: Der Docker-Healthcheck oder das `depends_on` des Frontends hängt nicht vom Zustand der Sicherung ab. `/health` meldet den Zustand weiterhin, wie O1 verlangt, etwa im Body oder über eine eigene Prüfung.

## C-2: R1 bricht beim nächsten Release

`OLD=$(mktemp -d)` ist ein absoluter Pfad, `path.join` setzt ihn aber nicht zurück. `node -e "console.log(require('path').join('/repo','/tmp/tmp.abc/backend','src/services/backup-crypto.ts'))"` gibt `/repo/tmp/tmp.abc/backend/src/services/backup-crypto.ts` aus. Heute läuft nur der Zweig `backup backend` mit relativem Pfad (upgrade-check.sh:66), weil v0.99.35 noch kein `backup.service.ts` hat. Der Zweig, den R1 eigentlich prüft (eine Sicherung mit dem Backend der Vorversion), ist deshalb nie gelaufen und scheitert beim ersten Mal. Abhilfe: `resolve(backend, …)` oder `join(backend, …)` ohne `process.cwd()`.

## C-3: Keine dokumentierte Sicherung zwischen Teil 1 und Teil 2

Jeder Push auf `main` ist ein Release (fitness-functions.md, `upgrade`). Nach dem Merge steht in der Anleitung nur noch die automatische Sicherung, «once the landlord has confirmed the Wiederherstellungscode». Bestätigen lässt sich der Code aber erst mit Teil 2. Der Betreiber hat damit bis dahin keine dokumentierte Sicherung, und ein bestehender Klartext-Dump lässt sich nicht mehr nach Anleitung einspielen. Abhilfe: Die manuellen Befehle bleiben, bis Teil 2 den Code bestätigbar macht, z. B. als «solange kein Wiederherstellungscode bestätigt ist».
