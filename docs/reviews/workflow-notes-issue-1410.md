# Workflow notes #1410

| Rule | What happened | Proposal |
|---|---|---|
| `CLAUDE.md`, "Before marking anything complete": `bun run fitness -- --base origin/main --structure` | Fitness measures the maintainability of the **committed** HEAD (in worktrees), but a run on uncommitted changes printed «0 errors» because HEAD did not contain them yet. Two maintainability errors appeared only after the frontend commit. Each try at a fix then needed a commit (or an amend) to be measured. | Say in the rule (and in the fitness output) that `--structure` measures HEAD, not the working tree, so it runs after the commit of a slice. Or let the commit hook run `--structure` too. |
| `CLAUDE.md`, "Gotchas", Formatting («format only your own lines») | The files a change touches are often not Prettier-clean (overview.ts 56, invoice-pages.dom.test.ts 244 differing lines on `main`). Formatting only my own lines needed a small script (difflib over `git diff -U0`), and the first try with `prettier --write` on a file that looked clean changed 5 foreign lines. | Ship such a script as `bun run format:own <file>` (format the hunks the branch changed), or name the check `git show origin/main:<f> \| bunx prettier --stdin-filepath <f>` in the rule. |
| Fitness fat-file / fat-module ratchets (#1272) | Small additions (one field, one import) hit the line ratchets of `schema.ts`, `types.ts`, `overview.ts` and the module-dependency limit of `fe:routes/invoices`. Each needed an unrelated move or compaction (`EarlierSize` inlined, `inPeriod` moved, a comment merged into a line, a type taken from `PageData`). | Allow a few lines of slack per file on a feature slice, or report the ratchets in the hook before the commit instead of after. |
| Persona README «A change that adds a screen or flow gets every persona» | All five personas ran on one shared `dwello_persona`. Two of them saved (delete, «Behalten») while three read, so Dr. Weber and Anna saw records change under them and could not follow some tasks. | Give personas that save in parallel their own records (SQL per persona, as done here for Sven), or order the saving ones after the reading ones. |
