## C-1 (Major): Commit-Gate prüft Dwello-Commits in Worktrees ausserhalb des Projektordners nicht mehr

Warum falsch: `inProject` vergleicht das aufgelöste Verzeichnis mit dem Ordner des Hooks (`relative(project, dir).startsWith('..')`). Ein Worktree von Dwello unter `<scratchpad>/…` liegt ausserhalb dieses Ordners, gehört aber zum selben Repository. Für Sessions und Subagents, die committen, verlangt `CLAUDE.md` (Gotchas, «Branches») einen eigenen Branch per «`git worktree add -b <branch> …`»; deren Commits landen auf Dwello-Branches und werden gepusht. Keine CI-Prüfung fängt Betreffzeilen ab (`.github/workflows` durchsucht: keine Commit-Message-Prüfung). Ausserdem widerspricht der Code der neuen Regel: `CLAUDE.md:97` sagt «commits in a repository outside the project (a scratch repository) pass». Gemeint ist das Repository, geprüft wird aber das Verzeichnis. Verlangt war: «passes commits outside the project and still blocks inside it».

So zeigt man den Fehler (nur lesend, Hook des Worktrees mit `project` = Worktree):

```
jq -nc --arg c "git commit -m 'bad.'" --arg d /tmp/claude-0/other-dwello-worktree '{tool_input:{command:$c},cwd:$d}' \
  | node <worktree>/.claude/hooks/commit-msg-gate.mjs; echo $?   # 0
```

Für den Haupt-Checkout als Projekt gilt dasselbe mit `cwd` = `<scratchpad>/review-rules-code-reviewer`. Dessen `git rev-parse --git-common-dir` ist `/home/user/Dwello/.git`, der Hook liefert trotzdem Status 0. `commit-msg-gate.test.ts` hat keinen Fall «Worktree des Projekts ausserhalb des Ordners». Lösung: nach Repository entscheiden (`git -C <dir> rev-parse --git-common-dir` gegen den Wert des Projekts), dazu ein Test, der vorher rot ist.

## C-2 (Major): «No scenario» für die Anzeige einer Ablehnung ist zu breit

Warum falsch: `CLAUDE.md:53` zählt «how the UI shows a refusal's body (a DOM test with the body from a contract)» zu den Zuständen, die der E2E-Stack nicht erzeugen kann. Gemeint war in 127 R-1 eine Ablehnung, die die eigene Prüfung der UI nie zum Backend durchlässt, sodass nur `FailRequests` (500 ohne Body) sie erreicht. Der E2E-Stack läuft aber gegen das echte Backend und erzeugt viele Ablehnungen über die UI. Die Features prüfen heute schon die Texte von `backend_formula_invalid`, `backend_formula_not_computable`, `backend_heating_profile_shares_sum`, `backend_distribution_key_predefined`, `backend_heating_profile_predefined` und `backend_statement_not_found` (Abgleich `messages/de.json` gegen `tests/e2e/features`). Als Beispiel formuliert, deckt der Satz jeden Fehler «Ablehnung zeigt Rohtext» ohne Szenario ab, auch wenn die Ablehnung durch Eingabe erreichbar ist. Damit fällt ein für Nutzer sichtbarer Bugfix unter Schritt 1 ohne Szenario durch. Der `code-reviewer` meldet ein fehlendes Szenario als Major.

So zeigt man den Fehler: Ein Bug «die Meldung zu `FORMULA_INVALID` zeigt den Backend-Text» würde nach dem neuen Wortlaut mit DOM-Test und `No scenario: <reason>` abgeschlossen. Ein Szenario dafür lässt sich mit dem echten Backend aber schreiben (die bestehenden Szenarien zu Verteilschlüssel-Formeln tun das). Lösung: einschränken auf «a refusal the UI's own checks never send to the backend».
