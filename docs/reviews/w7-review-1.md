## C-1 (Major): Wettlauf im Szenario #141

**Warum falsch.** Der Schritt «… auf den "2024-06-30" beendet und die Folge bestätigt» ruft `endContractOn(date, { confirmPast: true })`. Der Task endet mit `Click.on(confirmEndContractButton)` und wartet nicht auf den Zustand, zu dem der Klick führt: die Ablehnung mit dem Angebot «Entwurf löschen und beenden». Danach legt `seed.statement` sofort über die API die Abrechnung 2025 an. Ist diese Abrechnung gespeichert, bevor das BFF (`endDay` → GET, dann PUT) das Backend fragt, lehnt das Backend mit zwei Abrechnungen ab. Dann bietet der Dialog das Löschen des einen Entwurfs nicht an, und `Click.on(deleteDraftAndEndButton)` läuft in den Timeout. Das verletzt die Regel aus `tests/e2e/CLAUDE.md`: Tasks warten auf den Zustand, zu dem sie führen. Bei parallelen Läufen in der CI wird das Szenario flackern.

**Wie zeigen.** Den Seed-Schritt mit einer künstlichen Verzögerung im BFF-Pfad laufen lassen, z. B. `FailRequests` nicht nötig, einfach `page.route` auf `?/endDeletingDraft` mit 500 ms Verzögerung. Oder die Reihenfolge Seed vor Klick erzwingen: das Szenario scheitert dann am fehlenden Button. **Fix:** vor dem Seed auf das Angebot warten, z. B. mit einem Schritt «Dann bietet der Dialog an, den Entwurf zu löschen» (Frage auf `deleteDraftAndEndButton`), oder `Wait.until(deleteDraftAndEndButton)` in einem eigenen Task.
