# Workflow notes: #817 (MCP server with Zugangsschlüssel für KI-Programme)

| Rule | What happened | Proposed change |
|---|---|---|
| `CLAUDE.md`, Workflow 1 («Scenarios are the specification»), with `privacy.feature` «Stand der Datenschutzerklärung» and `terms.feature` «Stand der Nutzungsbedingungen» | Each change of a legal text also changes the «Stand» date, which two scenarios pin to a fixed day. So every legal text change becomes a spec change that waits for the product owner, also when the issue already decided the text. Two other scenarios pin whole old sentences (`privacy.feature:43`, `terms.feature:30`), so the domain review's additions had to go into sentences of their own. | Let an issue whose «Decided (product owner)» decides a legal text also approve the «Stand» date in the same pull request, or let the scenario check that a «Stand» is shown and lies at or after the last change of the legal texts, instead of a fixed day. |
| `src/__tests__/no-german-in-code.test.ts` | A new German message containing «lang» («100 Zeichen lang») made `%lang%` in `src/hooks.server.ts` and `src/lib/server/statement.ts` count as German in code; the check failed in two files the change did not touch. | Leave out of the word list words shorter than 5 letters, or words that are also code identifiers (`lang`), so a message cannot make unrelated code fail. |
| `docs/test-pyramid.md` / `tests/e2e/CLAUDE.md`, «No scenario», failure states | Code review asked twice (817-1 C-2, 817-2 C-2) for scenarios of the refusals «nicht erstellt» and «nicht widerrufen»; both come only from a failing call between web app and backend, as `FailRequests` gives an empty 500 that `enhance` treats as an error, not a failure. The point was settled only in the third round. | In «Failure states», say that `FailRequests` reaches the page's error handling, not a form action's `fail()`, so a refusal the action builds from a failing backend call is «a failure only between server parts». |
