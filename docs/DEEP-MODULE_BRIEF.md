# Deep Module Brief

Single source of truth for the internal tool **deepcheck**. Every work session reads this file first, does its phase, and appends to the Status Log at the bottom. If the brief and a prompt disagree, the brief wins. Change the brief, not the prompt, when decisions change.

## 1. Purpose

deepcheck finds shallow modules in this TypeScript codebase and enforces deep modules on changed code.

- Deep module: small, simple interface hiding a lot of implementation.
- Shallow module: interface is large relative to the functionality it provides; it hides little complexity.
- Basis: John Ousterhout, *A Philosophy of Software Design*, ch. 4 ("Modules Should Be Deep"); information hiding per Parnas (1972).

deepcheck is a warning system built on measurable proxies. It is not a verdict on design quality. The README must say so and list known false-positive sources.

## 2. Non-goals

- No LLM calls inside the tool, no auto-fix.
- No refactoring of existing application code to satisfy the tool.
- No changes to existing CI steps, their order, or repo/branch-protection settings. Only add.
- No type-checking or linting duties (tsc, ESLint) and no duplication of what Fallow gates (dead code, duplication, cycles).

## 3. Conventions and constraints

- Discover first: package manager, TypeScript version/tsconfig, module system, test framework, lint/format rules, folder layout. Follow them. In a monorepo, add the tool as a private workspace package, never published.
- Use `ts-morph`, pinned to a version compatible with the repo's TypeScript. Add only necessary devDependencies.
- Fallow is the reference for wiring. Inspect how it is set up (package scripts, config, `.claude/` hooks, AGENTS.md/CLAUDE.md, git hooks, GitHub Actions) and mirror it. Run it and observe its real JSON (`npx fallow audit --format json --quiet`, `npx fallow schema`). Exit codes 0 and 1 both mean the run succeeded, 2 is an error.
- Check current Claude Code hooks documentation for event names and exit-code semantics; do not rely on memory.
- Output must be deterministic. Ordering stable across runs.

## 4. Metrics

Module = source file; also report per exported class. Document exact formulas in the README.

| Metric | Definition |
|---|---|
| interfaceSize | exported symbols + parameter count of exported functions/methods + public members of exported classes (+ their parameters) |
| implementationSize | non-blank, non-comment statements of the whole module, including non-exported code |
| depthRatio | implementationSize / max(1, interfaceSize) |
| passThroughs | functions/methods whose body only forwards their parameters, in order, to another call (AST detection); report each location |
| leakyExports | exported signatures referencing types that are internal or not exported from the module (type resolution, conservative) |
| classitis | directories with many files that each have one tiny export; classes made only of getters/setters/fields |
| coupling | fan-in and fan-out from the import graph, respecting tsconfig paths. Deep modules tend to have high fan-in, low fan-out |
| complexity | from Fallow if available, else own cyclomatic count |

`shallowScore` is 0 to 100, higher means more suspicious, with documented default weights. A configurable minimum interfaceSize prevents flagging tiny legitimate utilities (e.g. `clamp`), unless they are pass-through or classitis cases.

Default exclusions (all configurable): tests, `*.d.ts`, generated files, type-only files (DTOs/interfaces), barrel files with only re-exports, paths already ignored as generated by the Fallow config.

Fallow is optional enrichment (unused exports, complexity, cycles) via its JSON output in ONE adapter file, typed from the observed real output. Flag `--fallow auto|off|<path>`. Everything must work with `off`. deepcheck must not fail on findings Fallow already gates; it only uses them as score inputs.

## 5. Scopes

| Scope | Command | Purpose | Blocks? |
|---|---|---|---|
| changed | `deepcheck check` / `--scope changed` | agent loop and PR gate | yes, per gates below |
| all | `deepcheck scan [path]` / `--scope all` | list ALL shallow modules in the codebase, including legacy | no, exit 0 unless `--fail-on-score` is given |

Changed set:
- Dev/agent loop: working tree + staged changes vs HEAD, plus untracked TS files.
- CI: diff against the merge-base with the PR base branch (`--changed-since <ref>`).
- The whole-project import graph is always built; only reported and failing findings are narrowed.

`scan` options: `--top <n>` (default 50), `--min-score`, `--group-by directory|package`, `--format human|json|markdown|github`, `--output <file>`, `--use-baseline` (hide baselined findings), a path argument for limiting to a package or directory.

## 6. Gates (enforcement rules)

These are the only rules that make deepcheck fail a run.

- **G1 New module gate:** a changed module that is new and has `shallowScore >= failThreshold` fails.
- **G2 Regression gate:** a changed module that exists in the baseline fails if its score worsened by more than `tolerance` and is `>= failThreshold`.
- **G3 Legacy rule:** unchanged modules and baselined modules that did not worsen never fail the changed scope. They only show up in `scan`.
- **G4 Suppression rule:** inline suppressions require a reason; a suppression without reason is itself a finding. `deepcheck suppressions` lists them.
- **G5 Tool-error rule:** tool or config errors exit 2, never 1, so errors are not mistaken for findings.
- **G6 Fallow independence:** the gate result is identical with `--fallow off`, except for score inputs that depend on Fallow data, which fall back to own computation.

Exit codes: 0 ok, 1 gate failed, 2 tool/config error (JSON error envelope on stdout with `--format json`).

Defaults for `failThreshold` and `tolerance` are calibrated from data in Phase 4 and recorded in the Status Log. Until then use conservative values.

## 7. Baseline

- File: `.deepcheck-baseline.json`, committed. Stable fingerprints (module path + rule id, no line numbers) plus the score at baseline time.
- `deepcheck baseline` creates or updates it. Handles deleted and renamed modules without crashing.
- The initial baseline is generated from the current repo state. Record how many modules are above the threshold.

## 8. Output

- Formats: `human`, `json` (stable typed schema, types exported, JSON schema shipped), `markdown`, `github` (workflow annotations + step summary markdown).
- Agent mode: top findings first, capped, silent when clean.
- Each finding names the module, the failing metric(s), and a concrete fix in Ousterhout terms (merge pass-throughs into the callee, shrink the exported surface, combine tiny classes, hide implementation details behind the interface). Every finding states: fix the design, do not pad the implementation to game the ratio.
- `--explain <file>` shows all metrics and why the score is high.
- Config: `deepcheck.config.json` with shipped schema (include/exclude, thresholds, weights, per-path overrides, minimum interfaceSize, failThreshold, tolerance).
- Inline suppression: `// deepcheck-ignore-file -- reason` and `// deepcheck-ignore-next-line <rule> -- reason`.

## 9. Wiring

- Package scripts, named consistently with existing ones: `deepcheck:audit` (changed vs HEAD, agent mode), `deepcheck:ci` (changed vs PR base, github format), `deepcheck:scan` (full scope), `deepcheck:baseline`.
- After every implementation step: run `deepcheck:audit` through the same mechanism Fallow uses (Claude Code hook and/or commit/push gate and/or git hook). Fast, non-interactive, silent when clean, never hangs or loops. Only the changed scope runs here, never the full scan.
- AGENTS.md / CLAUDE.md: after each implementation step run the audit script and fix findings before continuing; run the scan script only when a codebase-wide review is requested.
- GitHub Actions, PR workflow: add ONE new blocking step/job in the style of the existing steps (same setup, caching, runner, pinned versions). `fetch-depth: 0` (or the repo's equivalent), run `deepcheck:ci` against the PR base, write annotations and a step summary, fail on gate failure.
- GitHub Actions, `deepcheck-scan.yml`: `workflow_dispatch` only (inputs: optional path, top N, min score). Runs the scan, writes the ranked report to the job summary, uploads JSON/markdown as an artifact. Never blocks. Includes a commented-out weekly `schedule` example.

## 10. Phases and exit gates

Work happens in phases. A phase is done only when ALL its exit gates are verified and logged. Recommended order: Phase 1, Phase 2, Phase 4, Phase 3, so results are validated before the tool blocks anything in hooks or CI.

### Phase 1: Core and scan
Build the CLI, metrics, config, suppression, output formats and `scan`. No baseline, hooks or CI.
- X1.1 Existing repo checks (lint, typecheck, tests, Fallow) still pass; new tests pass.
- X1.2 Fixtures (deep module, shallow module, barrel, DTO, tiny utility): deep scores lower than shallow, pass-throughs detected, exclusions respected.
- X1.3 Works with `--fallow off`; Fallow adapter tested with recorded real JSON.
- X1.4 `deepcheck scan` runs on this repo. The top results were inspected by hand and obvious false positives were fixed in the tool, not hidden.
- X1.5 README section: formulas, config, known false positives.

### Phase 2: Gate
Baseline and changed scope implementing G1 to G6.
- X2.1 Tests for each gate: new shallow module fails (G1), worsened module fails (G2), legacy module does not fail but appears in `scan` (G3), reasonless suppression is a finding (G4), errors exit 2 (G5), same result with `--fallow off` (G6).
- X2.2 In a scratch working tree a deliberately shallow temporary module makes `audit` fail with an actionable message and `ci` fail against a base ref; after removal the clean tree passes.
- X2.3 Baseline committed; count of modules above threshold recorded.
- X2.4 Changed-scope runtime measured and low enough for a per-step hook (target: a few seconds); number recorded.

### Phase 3: Integration
Hook after every step, PR step, scan workflow, docs.
- X3.1 The after-step mechanism fires the way Fallow's does; how it was verified is logged.
- X3.2 PR step added in the repo's style; scan workflow valid. Lint with actionlint or repo tooling if available; simulate with `act` if available, otherwise dry-run the exact commands against a base ref.
- X3.3 A deliberately shallow temp module is caught by both the hook path and the CI command, then removed.
- X3.4 README, AGENTS.md/CLAUDE.md updated. Anything not verifiable is stated explicitly.

### Phase 4: Validation and calibration
Prove the results are meaningful before the PR gate is trusted. Only scoring, thresholds, weights, exclusions, detectors, tests and docs may change.
- X4.1 Labeled sample: top 25, a random 15 from the middle (fixed seed, recorded), and the 15 lowest-scoring non-trivial modules. Each labeled truly shallow / truly deep / legitimately flat by design, with a one or two sentence reason in Ousterhout's terms. Labels are critical, not tool-confirming.
- X4.2 Precision of the top 25 reported before and after calibration; false positives grouped by cause; each cause fixed in the tool with a regression test written first.
- X4.3 Reference check: fixtures for well-known deep and shallow designs ordered correctly; 2 or 3 well-regarded open-source TypeScript projects (cloned into a temp dir, never into this repo) spot-checked on their top 10.
- X4.4 Gaming tests: padding a shallow module with dead internals, splitting a deep module into tiny files (score must go up), inlining pass-throughs (score must go down). Mitigate or document each weakness.
- X4.5 Ablation per metric; noisy metrics dropped or down-weighted, stated explicitly.
- X4.6 Recommended `failThreshold` and `tolerance` chosen from data, with the number of modules above it.
- X4.7 Report `docs/deepcheck-validation.md` with the labeled table, numbers, limits (small sample, one codebase, judgment labels) and a verdict: "ready to gate on changed code", "usable as scan only", or "not ready".

### Consequences of the Phase 4 verdict
- "not ready": stop; do not do Phase 3; report what must improve.
- "usable as scan only": do Phase 3 but wire only `deepcheck-scan.yml` and the docs. Do NOT add the blocking PR step or the after-every-step hook.
- "ready to gate on changed code": do Phase 3 completely.
- If Phase 4 changes scoring, regenerate the baseline and re-run the Phase 2 gate tests before Phase 3.

### Cross-cutting exit gates (every phase)
- XC.1 Every logic change has a test that was seen failing first (see section 11), with red/green evidence logged.
- XC.2 Every step group passed the independent review (section 11) or open disagreements are logged.
- XC.3 Everything is committed in small logical commits; the Status Log is updated.
- XC.4 No changes outside scope: no application code, no existing CI steps, no repo settings.

## 11. Working rules for the agent

- Read this brief and the Status Log first. Re-read the Status Log before starting each phase.
- Record decisions and deviations in the Status Log, not only in chat.
- Never mark an exit gate as done without having run the check; log how it was verified.
- If something cannot be verified (hook behavior, CI behavior), say so plainly.
- Keep commits small, in logical steps, with clear messages.

### Test-driven development
- **Strict TDD** for gates (G1 to G6), exit codes, baseline logic, config validation, suppression handling and the Fallow adapter. Work in red-green-refactor cycles of ONE behavior each: (1) write one small test for one behavior and run it; it must fail for the right reason (not a typo or import error); (2) write the minimum code to make it pass; (3) refactor with all tests green and re-run them. Commit after each green+refactor with a message naming the behavior. Do not write several tests or a large implementation at once.
- **Test-first with fixtures** for the metrics and scoring: write the fixture and the expected ordering or values first, confirm they fail, then implement. Larger steps are acceptable here, but never write the implementation before the failing test.
- **Failing check first** for work that cannot be unit-tested (workflows, hooks, docs): use a check that must fail before and pass after (actionlint, a dry run of the exact command, a script that asserts the file content).
- **Exploratory work** (Phase 4 labeling, calibration, ablation) is exempt from TDD, but every fix it produces needs a regression test written first.
- If a step genuinely cannot be tested first, say why in the Status Log.
- Log which cycles were done and the red/green evidence.

### Independent review after every step group
- After each group of related behaviors or each logical implementation step (a cluster of commits that delivers one capability, e.g. "pass-through detection complete", "baseline logic complete"), spawn a review subagent with the Agent tool. The reviewer has not seen the work being produced.
- Give it this brief, the diff, and the relevant exit gates. Ask it to check: gates and exit criteria met; tests are meaningful (they would fail if the behavior broke, not just execute lines); no changes outside scope (no application code, no existing CI steps); no gaming of the score; no unverified claims; code and messages follow the brief.
- Fix every valid finding before continuing. At most two review rounds per step group; log remaining disagreements in the Status Log instead of looping.
- Review per group, not per single test, to keep cost reasonable. At the end of each phase run one final review of the whole phase against its exit gates.

### Reporting
- Final summary per phase: what was found, decisions made, key numbers, review findings that mattered, uncertainties, recommended next step.
