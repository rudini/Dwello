# Stage 3: does the skill produce deeper modules?

A three-arm comparison on small tasks, rated blind. All numbers in `results/` and `REPORT.md` come from `harness/stage3`; nothing is entered by hand.

## Material

- `FIXTURES.md`: the fixture format. `fixtures/` holds the 4 visible tasks, `holdout/` the 2 hold-out tasks. A separate subagent wrote all six and validated them (starter green, hidden tests red on the starter, green on the reference). The experimenter does not open `holdout/` before the final run; the harness copies it mechanically.
- `arms/`: what each arm is told in front of the task text. The task text (`task.md`) and the closing paragraph (`arms/common.md`) are identical for all arms.
  1. `baseline`: nothing.
  2. `canon`: Kent Beck's Canon TDD in five steps (`canon-tdd.md`).
  3. `skill`: "Use the tdd-deep-modules skill for this task." The run repository holds a copy of the skill (SKILL.md, references, scripts without their tests) under `.claude/skills/`, so Claude Code loads it with its hook; arms 1 and 2 get no `.claude/` directory.

## Isolation

Every session (arm or reviewer), and every command that runs an arm's code (its own tests, the hidden tests, `tdd_replay`), runs in fresh mount and PID namespaces (`harness/sandbox.sh` under `unshare -m -p -f --mount-proc`). Its directory is mounted at `/workspace`; empty tmpfs mounts hide `/home/user` (the Dwello checkout with `evals/` and `evidence/`), all of `/tmp` (every run, review view and result, the tool caches that hold copies of the checkout), `/root/.claude` and `/root/.cache` (other sessions' transcripts, tasks, scratchpads and logs), `/mnt` and `/srv`; the PID namespace hides every other process and its `/proc/<pid>/root`. The command then runs in a new user namespace, where these mounts are locked: even its root cannot unmount them. Inside the sandbox a search of every filesystem for the experiment's names (the checkout, `stage3`, fixture and test file names, the session ids, tool caches) finds nothing.

A session gets an allowlisted environment: no GitHub, cloud or git credentials, no parent-session identity, no extra directories, no Dwello `CLAUDE.md`, skills or hooks (arm 3 has its copy of the skill). Its shells source `/sandbox/env.sh` (`harness/sandbox-env/env.sh`): commands run without the network proxy and git accepts only local repositories (`GIT_ALLOW_PROTOCOL=file`, no global git config); only the Claude Code process itself keeps its API connection. Tools are an explicit set (`--tools`, no MCP servers): arms get Read, Write, Edit, Glob, Grep, Bash and Skill, reviewers Read, Glob and Grep; nothing else exists in a session (no web, subagents, artifacts, messaging, plugin or connector search). Edits only inside `/workspace`; Bash runs without a prompt only for `bun`, `bunx`, `git`, `ls`, `mkdir`, `cat`, `head`, `tail`, `wc`, `grep`, `echo`, `pwd`, `diff` and the skill's scripts, identically for every arm; Claude Code decides how it matches compound commands (in the smoke runs, a heredoc `cat > file <<EOF` was denied in the canon arm and arm 3's `S=...; $S/tdd-step` compounds were allowed), and every arm adapts to the same rules.

Each run's full transcript is kept (`results/runs/<id>.stream.jsonl.gz`). Every command or read (Bash, Read, Glob, Grep) with an escape signal is listed in `foreign_references`, and such a run is invalid (a rule fixed before any real run). Escape signals: `/home/`, `/tmp`, `/root`, `/mnt`, `/srv`, `/proc/<pid|self>`, `/sys/`, `/sandbox`, `/verifier`, `$HOME`, `~/`, the experiment's names (Dwello, stage3, holdout, evals/), URLs, github, proxy variables, network and namespace tools (`curl`, `wget`, `nc`, `socat`, `ssh`, `scp`, `mount`, `umount`, `unshare`, `nsenter`, `chroot`) and the credential file names; the session's own places (`/workspace`, its scratchpad and tool-result files, bun's cache) are removed before matching, so ordinary work (a division in a `bun -e` probe, a `'/'` literal) does not count. A reviewer with an escape signal counts as no review, and the group is reviewed again.

Limits of this isolation, stated plainly. It holds against accidental contamination and against simple attempts; it is a tripwire, not a barrier, against a session that sets out to escape: (1) the network is not cut off. A filtering egress proxy that admits only the API was refused by this environment's safety classifier, so a command that re-adds the proxy by hand can still reach the repository on GitHub. (2) Claude Code's credentials under `/home/claude` stay readable inside the sandbox, because the session needs them to authenticate. (3) Only commands and reads are scanned, not the content of files a session writes and then runs. (4) `/proc/self/mountinfo` shows the run directory's host path, which names the run id. Every such route needs a deliberate act the transcript records; the gate counts invalid runs per arm and reason, and `REPORT.md` reports them.

## A run (`harness/stage3 run <fixture> <arm> <run-id>`)

Run ids are `<phase>-<fixture>-<arm>-r<slot>-a<attempt>`. Nothing is overwritten: an existing run id is refused.

1. Copy `starter/` (plus the skill for arm 3) into a new repository and commit it as `start`.
2. Start the sandboxed session with preamble + task + closing paragraph.
3. Measure the final working tree (every command that touches the arm's repository or code, git included, runs in the sandbox; symbolic links are never followed): the arm's own `bun test`; the hidden tests (`hidden/` copied to `__acceptance__/`, `bun test ./__acceptance__`); the production files, i.e. the import closure of the modules the hidden tests import (test helpers that only tests import are not production); `depth_report` over them; for arm 3 whether the `Skill` tool loaded tdd-deep-modules, and `tdd_replay start..HEAD` with the skill's locked scripts (only `scripts/` is mounted, read-only). `depth_report` favours arm 3 by construction (that arm is told to run it and fix its findings), so it is a plausibility signal, never a depth verdict.
4. Keep `results/runs/<id>.json`, a git bundle and a tarball of the final tree.

Rules fixed before any real run: a run is invalid when its hidden tests fail, when its work is not committed (`tdd_replay` judges commits, reviewers see the tree), when it has a foreign reference, when the harness did not finish it (the record is written as `started` before the session begins), or (arm 3) when the skill was never loaded, so the treatment was not given. An invalid run stays in `results/` as a failure case and its slot is run again with the next attempt number. Attempts are numbered 1, 2, ... without gaps. The planned slots are fixed: slot 1 in the pilot, slots 1, 2 and 3 in the main phase, for every fixture and arm. The gate uses, per fixture, arm and slot, the first valid attempt and nothing else; it fails on a slot outside the plan, on a planned slot with no run or no complete review, on gaps, on any attempt after the first valid one, on run directories or transcripts without a record, and when a valid arm-3 run in `results/` (reviewed or not) lacks `tdd_replay` ACCEPT.

## Blind review (`harness/stage3 review <group> <fixture> baseline=.. canon=.. skill=..`)

One group (`<phase>-<fixture>-r<slot>`) = one fixture and one slot, i.e. the first valid run of each arm. Two reviewers, each a fresh sandboxed session without Bash, edits or skills, get `TASK.md` and the three implementations' production code under random letters (a new shuffle per reviewer). Tests, Markdown, `.claude/`, git history and comments are removed; each file is reprinted by the TypeScript printer, so layout and comments cannot reveal the arm. The rubric is Ousterhout's definition only (a deep module's interface is small and simple compared with the functionality and design decisions it hides; a shallow module's interface is about as complex as what it does), without the skill's own checklist, so reviewers do not score conformance to what arm 3 is told. Each reviewer scores module depth from 1 to 10 per implementation. The harness turns scores into two comparisons: skill vs baseline and skill vs canon (+1 deeper, 0 equal, -1 shallower). If the two reviewers differ on either comparison, a third reviewer (new shuffle) rates the group and the majority of the three decides; without a majority the comparison is 0. A group whose disagreement has no complete third review counts as not reviewed. Reviews are never overwritten; a review that crashed or gave no complete scores is repeated as `<group>.<attempt>` (2, 3, ...; all reviewers again), and the gate uses the first complete attempt, lists all, and fails on gaps and on any attempt after a complete one.

Pilot groups add a control: the baseline implementation appears twice under different letters. The gate prints each pilot reviewer's control delta; a delta above 1 marks the reviewer UNRELIABLE. `gate --phase pilot` prints `PILOT: OK` only when 2 fixtures were reviewed with every planned run and no UNRELIABLE control; the main gate requires that, so the rubric must be revised and the pilot repeated (as a new pilot) before main runs count.

## Plan

1. Pilot: 2 visible fixtures x 3 arms x 1 run, reviewed with the control. Checks the harness end to end and the reviewers' consistency.
2. Main: 4 visible fixtures x 3 arms x 3 runs (fresh runs, pilot runs are not reused).
3. Hold-out: 2 hold-out fixtures x 3 arms x 3 runs, opened only now.
4. `harness/stage3 gate` prints every group's raw scores and the per-fixture tallies, then `STAGE3: PASS` only when: the pilot is OK; every group reviews the first valid attempt of each arm's slot; `tdd_replay` accepted every valid arm-3 run; for each of the 6 fixtures, all 3 run groups were reviewed, the skill was rated deeper than baseline in a majority of them and shallower in none; the latest review of each stage-3 step (14-17) ends in `VERDICT: PASS`; `REPORT.md` exists. It also prints whether attribution to the skill over plain TDD is supported (skill deeper than canon in a majority of each fixture's runs) or unproven. That line is reported, not gated.

Every step ends with the review gate: a fresh read-only reviewer, every blocker or major finding fixed, a new reviewer verifies; after 3 failed rounds the work stops. (Step 14 failed rounds 1-3; the user then ordered a new review cycle, rounds 4-6.)
