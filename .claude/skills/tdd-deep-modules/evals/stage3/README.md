# Stage 3: does the skill produce deeper modules?

A three-arm comparison on small tasks, rated blind. All numbers in `results/` and `REPORT.md` come from `harness/stage3`; nothing is entered by hand.

## Material

- `FIXTURES.md`: the fixture format. `fixtures/` holds the 4 visible tasks, `holdout/` the 2 hold-out tasks. A separate subagent wrote all six and validated them (starter green, hidden tests red on the starter, green on the reference). The experimenter does not open `holdout/` before the final run; the harness copies it mechanically.
- `arms/`: what each arm is told in front of the task text. The task text (`task.md`) and the closing paragraph (`arms/common.md`) are identical for all arms.
  1. `baseline`: nothing.
  2. `canon`: Kent Beck's Canon TDD in five steps (`canon-tdd.md`).
  3. `skill`: "Use the tdd-deep-modules skill for this task." The run repository holds a copy of the skill (SKILL.md, references, scripts without their tests) under `.claude/skills/`, so Claude Code loads it with its hook; arms 1 and 2 get no `.claude/` directory. The copy is the skill as it is: its SKILL.md mentions Dwello's `bun run deepcheck:audit` as an example of a project depth gate, which the run repositories do not have (the skill says to run it only where the project has one).

## Isolation

Every session (arm or reviewer), and every command that runs an arm's code (its own tests, the hidden tests, `tdd_replay`), runs in fresh mount and PID namespaces (`harness/sandbox.sh` under `unshare -m -p -f --mount-proc`). Its directory is mounted at `/workspace`; empty tmpfs mounts hide `/home/user` (the Dwello checkout with `evals/` and `evidence/`), all of `/tmp` (every run, review view and result, the tool caches that hold copies of the checkout), `/root/.claude` and `/root/.cache` (other sessions' transcripts, tasks, scratchpads and logs), the tool credentials and logs under `/root` (`.npm`, `.ssh`, `.aws`, `.config`, `.local`; `.gitconfig`, `.boto`, `.netrc`, `.npmrc` read as empty), `/mnt` and `/srv`; the PID namespace hides every other process and its `/proc/<pid>/root`. The command then runs in a new user namespace, where these mounts are locked: even its root cannot unmount them. Inside the sandbox a search of every filesystem for the experiment's names (the checkout, `stage3`, fixture and test file names, the session ids, tool caches) finds nothing; what stays visible under `/root` is Claude Code's `.claude.json` and the proxy CA in `.ccr`, which the session needs, and toolchains (`.bun`, `.cargo`, `.rustup`, ...).

A session gets an allowlisted environment: no GitHub, cloud or git credentials, no parent-session identity, no extra directories, no Dwello `CLAUDE.md`, skills or hooks (arm 3 has its copy of the skill). Its shells source `/sandbox/env.sh` (`harness/sandbox-env/env.sh`): commands run without the network proxy and git accepts only local repositories (`GIT_ALLOW_PROTOCOL=file`, no global git config); only the Claude Code process itself keeps its API connection. Tools are an explicit set (`--tools`, no MCP servers): arms get Read, Write, Edit, Glob, Grep, Bash and Skill, reviewers Read, Glob and Grep; nothing else exists in a session (no web, subagents, artifacts, messaging, plugin or connector search). Edits only inside `/workspace`; Bash runs without a prompt only for `bun`, `bunx`, `git`, `ls`, `mkdir`, `cat`, `head`, `tail`, `wc`, `grep`, `echo`, `pwd`, `diff` and the skill's scripts, identically for every arm; Claude Code decides how it matches compound commands (in the smoke runs, a heredoc `cat > file <<EOF` was denied in the canon arm and arm 3's `S=...; $S/tdd-step` compounds were allowed), and every arm adapts to the same rules.

Each run's full transcript is kept (`results/runs/<id>.stream.jsonl.gz`). Every command, read and write (Bash, Read, Glob, Grep, Write, Edit) is checked for escape signals (`escapes()` in the harness), and a run with any is invalid (a rule fixed before any real run). Signals: a path that, after normalisation (`..`, `~`, `$HOME`, repeated leading slashes, the directory a command's `cd`/`pushd` reach, starting at `/workspace`; a bare `cd` goes to `/root`), lies under a sensitive top-level entry (`/home`, `/root` except `.bun` and `.claude`, `/proc` except `cpuinfo`, `meminfo`, `version`, `/sys`, `/run`, `/var`, `/dev` except the null and std devices, `/mnt`, `/srv`, `/boot`, `/media`, `/old_root`, `/sandbox`, `/verifier`, ...), with globs matched (`/h*`, `/{home,root}`); `/` or `/root` as an operand of a listing or searching command (`ls`, `find`, `du`, `tree`, `cp`, `tar`, `grep -r`, ...) or as a Glob or Grep path; network, process and namespace tools at command position, after shell keywords and wrappers (`curl`, `wget`, `nc`, `ssh`, `env`, `printenv`, `ps`, `mount`, `unshare`, `nsenter`, `strace`, ...), also inside `bash -c`/`sh -c`; proxy variable names, `process.env`, `Bun.env`, `os.environ`, credential file names and the experiment's names (`stage3`, `holdout`) outside heredoc bodies (the project name is not a signal: only arm 3's skill copy mentions it, and paths into the checkout are caught as paths). Variable assignments, `echo`/`printf` arguments, `$(...)` and quoted code strings are checked too. Commands are tokenised once, with quotes respected, heredoc bodies dropped and unquoted newlines as separators; the first operand of `grep`, `rg`, `sed`, `awk` and `perl` is a pattern, not a path. Ordinary work therefore does not count: slash-led text (`/money`, `/100`, `/-/g`, a `'/'` pattern), globs (`src/*/*.ts`), divisions and regex literals in `bun -e`, URL literals, `/tmp` (an empty tmpfs in the sandbox, holding the session's scratchpad), multi-line commit messages, code written through heredocs. The check was run on 52 ordinary and 46 escape commands from the reviews and on all 257 tool calls of the smoke transcripts (0 flagged). A reviewer with an escape signal counts as no review, and the group is reviewed again.

Limits of this isolation, stated plainly. It holds against accidental contamination and against simple attempts; it is a tripwire, not a barrier, against a session that sets out to escape: (1) the network is not cut off. A filtering egress proxy that admits only the API was refused by this environment's safety classifier, so a command that re-adds the proxy by hand can still reach the repository on GitHub. (2) Claude Code's credentials under `/home/claude`, `/root/.claude.json` and the proxy CA stay readable inside the sandbox, because the session needs them (hiding `/home/claude` was tested and breaks authentication). (3) The content of files a session writes and then runs is not scanned; paths built at run time or obfuscated (`readdirSync('/' + 'home')`, `readdirSync('/')` in code, `IFS` tricks, concatenated variables, base64) are not recognised; `$(...)` inside an unquoted heredoc body, shell builtins that print the environment (`export`, `set`, `declare -p`) and environment reads through a spawned process are not signals; each Bash call is judged from `/workspace`, although Claude Code keeps the cwd between calls (a rare false positive: after `cd src`, a later `ls ..` reads as listing `/`). (4) `/proc/self/mountinfo` shows the run directory's host path, which names the run id. Every such route needs a deliberate act the transcript records; the gate counts invalid runs per arm and reason, and `REPORT.md` reports them.

## A run (`harness/stage3 run <fixture> <arm> <run-id>`)

Run ids are `<phase>-<fixture>-<arm>-r<slot>-a<attempt>`. Nothing is overwritten: an existing run id is refused.

1. Copy `starter/` (plus the skill for arm 3) into a new repository and commit it as `start`.
2. Start the sandboxed session with preamble + task + closing paragraph.
3. Measure the final working tree (every command that touches the arm's repository or code, git and `depth_report` included, runs in the sandbox; symbolic links are never followed; the arm's `bunfig.toml` is removed before the hidden run, so no preload of its own can touch the hidden tests): the arm's own `bun test`; the hidden tests (`hidden/` copied to `__acceptance__/`, `bun test ./__acceptance__`); the production files, i.e. the import closure of the modules the hidden tests import (test helpers that only tests import are not production); `depth_report` over them; for arm 3 whether the `Skill` tool loaded tdd-deep-modules, and `tdd_replay start..HEAD` with the skill's locked scripts (only `scripts/` is mounted, read-only). `depth_report` favours arm 3 by construction (that arm is told to run it and fix its findings), so it is a plausibility signal, never a depth verdict.
4. Keep `results/runs/<id>.json`, a git bundle and a tarball of the final tree.

Rules fixed before any real run: a run is invalid when its hidden tests fail, when its work is not committed (`tdd_replay` judges commits, reviewers see the tree), when it has a foreign reference, when the harness did not finish it (the record is written as `started` before the session begins), or (arm 3) when the skill was never loaded, so the treatment was not given. An invalid run stays in `results/` as a failure case and its slot is run again with the next attempt number. Attempts are numbered 1, 2, ... without gaps. The planned slots are fixed: slot 1 in a pilot round, slots 1, 2 and 3 in the main phase, for every fixture and arm. The gate uses, per fixture, arm and slot, the first valid attempt and nothing else; it fails on a slot outside the plan, on a planned slot with no run or no complete review, on gaps, on any attempt after the first valid one, on run directories or transcripts without a record, and when a valid arm-3 run in `results/` (reviewed or not) lacks `tdd_replay` ACCEPT.

## Blind review (`harness/stage3 review <group> <fixture> baseline=.. canon=.. skill=..`)

One group (`<phase>-<fixture>-r<slot>`) = one fixture and one slot, i.e. the first valid run of each arm. Two reviewers, each a fresh sandboxed session without Bash, edits or skills, get `TASK.md` and the three implementations' production code under random letters (a new shuffle per reviewer). Tests, Markdown, `.claude/`, git history and comments are removed; each file is reprinted by the TypeScript printer, so layout and comments cannot reveal the arm. The rubric is Ousterhout's definition only (a deep module's interface is small and simple compared with the functionality and design decisions it hides; a shallow module's interface is about as complex as what it does), without the skill's own checklist, so reviewers do not score conformance to what arm 3 is told. Each reviewer scores module depth from 1 to 10 per implementation. The harness turns scores into two comparisons: skill vs baseline and skill vs canon (+1 deeper, 0 equal, -1 shallower). If the two reviewers differ on either comparison, a third reviewer (new shuffle) rates the group and the majority of the three decides; without a majority the comparison is 0. A group whose disagreement has no complete third review counts as not reviewed. Reviews are never overwritten; a review that crashed or gave no complete scores is repeated as `<group>.<attempt>` (2, 3, ...; all reviewers again), and the gate uses the first complete attempt, lists all, and fails on gaps and on any attempt after a complete one.

Pilot groups add a control: the baseline implementation appears twice under different letters. The gate prints each pilot reviewer's control delta; a delta above 1 marks the reviewer UNRELIABLE. `gate --phase pilot` prints `PILOT: OK` only when 2 or more visible fixtures (never hold-outs) were reviewed with every planned run, every pilot review carries the control copy, and no control is UNRELIABLE. A pilot round's depth results are printed but never judged, so no pilot is repeated because of how the arms compared. If a pilot round fails, the harness or rubric is fixed and a new round runs as phase `pilot2`, `pilot3`, ... (`gate --phase pilot2`); the main gate requires the latest pilot round to be OK. `harness/escape_samples.py` holds the escape-check samples of the reviews.

## Plan

1. Pilot: 2 visible fixtures x 3 arms x 1 run, reviewed with the control. Checks the harness end to end and the reviewers' consistency.
2. Main: 4 visible fixtures x 3 arms x 3 runs (fresh runs, pilot runs are not reused).
3. Hold-out: 2 hold-out fixtures x 3 arms x 3 runs, opened only now.
4. `harness/stage3 gate` prints every group's raw scores and the per-fixture tallies, then `STAGE3: PASS` only when: the pilot is OK; every group reviews the first valid attempt of each arm's slot; `tdd_replay` accepted every valid arm-3 run; for each of the 6 fixtures, all 3 run groups were reviewed, the skill was rated deeper than baseline in a majority of them and shallower in none; the latest review of each stage-3 step (14-17) ends in `VERDICT: PASS`; `REPORT.md` exists. It also prints whether attribution to the skill over plain TDD is supported (skill deeper than canon in a majority of each fixture's runs) or unproven. That line is reported, not gated.

Every step ends with the review gate: a fresh read-only reviewer, every blocker or major finding fixed, a new reviewer verifies; after 3 failed rounds the work stops. (Step 14 failed rounds 1-3; the user then ordered a new review cycle, rounds 4-6.)
