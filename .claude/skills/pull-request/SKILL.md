# Pull request

`CLAUDE.md`, "Done means", says when a task is ready for this; nothing is pushed before, except the draft of a session without subagents (Workflow 5), which stays a draft and is not merged until the missing reviews ran. Only the session that holds the product owner's task runs this skill, never a subagent or a session it started.

## Which pull requests

- One task, one pull request. Related issues of one request (they change the same files, texts, rows or screens, or the request names them together) are implemented together in one pull request with one `Fixes #n` per issue, and its description names each issue's scenario or `No scenario: <reason>`; one of them that turns out not to be ready gets `Refs #n`, a question in the issue and its place under "Blocked on me". Unrelated issues of one request get one pull request each; the closing report of each names the next.
- An issue the product owner allows to be split gets one pull request per part: `Refs #n`, the last one `Fixes #n`.
- A Blocker/Major whose fix is the decided text of another ready issue is fixed in the same pull request, which then closes both.
- A glossary term the product owner decided in the issue the task closes: when its «Decided (product owner)» names the rows, the task writes them into `UBIQUITOUS_LANGUAGE.md` and the pull request says so; otherwise the task finishes with that edit under "Blocked on me" (a marker would make CI refuse the pull request), and the pull request is merged only after the product owner made the edit.

## Before each push

1. Before the first push, merge `origin/main` once (no rebase, no force-push); later merges only as in "Open and drive". Then "Before marking anything complete" (`CLAUDE.md`) passes. Commit the reports, the plan and the archive (Workflow 8) before this push too: each later push cancels the CI run in progress and starts the full run again (only a push that changes nothing but documentation after a green run skips the tests).
2. Closing review: when code (`src/`, `backend/src/`, `backend/migrations/`, `messages/`, `tests/`, `tools/`, `.claude/hooks/`) changed since the last reviewed commit (Minor fixes, a conflict resolved in it, a CI fix), one `code-reviewer` round on that delta (skill `slice-review`), its own slice for the round limit. A merge of `main` counts only with a conflict resolved in `src/`, `backend/src/`, `backend/migrations/` or `messages/` (`git show --remerge-diff <merge>` shows it); a clean merge, or one resolved only in `tests/`, `docs/` or generated files, gets a line in the next round's prompt instead. A CI fix only in `tests/e2e/` (steps, fixtures, tasks) with a green run rides the next round, or the review of the merge it comes with, instead of a round of its own. So does a change only of test titles, or a Minor fix only in test files (`*.test.ts`, `tests/`), seen red where it changes what a test checks; and so does a change only of comments, or a Minor fix in app code that applies the report's own proposed fix, seen red where it changes behaviour (#1411): a line in the next round's prompt, and none of its own when no round follows before the push (workflow-rules-review-2026-11-08.md, 9). Only a Blocker/Major it reports gets another round. A delta only in generated ratchet limits (`tools/fitness/ratchet.json` from `--update`), in reports (`docs/reviews/`, persona reports in `docs/design/personas/`), `implementation_plan.md` or `docs/archive/` needs none, and the round's range leaves out the reviews, the plan and the archive (`git diff <base> <commit> -- . ':!docs/reviews' ':!implementation_plan.md' ':!docs/archive'`; with a merge of `main` in the delta: `git diff <last reviewed> <merge>^1`, its conflict resolution `git show --remerge-diff <merge>`, and `git diff <merge> <commit>` for what follows it, each with the same pathspec).

## Open and drive

- Push the branch, open the pull request in English with `Fixes #n` per issue (or `Refs #n` in the KI case, `backend/CLAUDE.md`) and the sections of `.github/pull_request_template.md`, «Type», «Decisions» and «Risks» filled in (CI checks them, #1271); subscribe to its activity. A change that needs a repository setting (labels, rulesets) lists the owner's commands under "Blocked on me" before the push. If the session cannot wait for CI, say under "Blocked on me" that the pull request waits for CI and is not merged.
- Merge a newer `main` into the open pull request only for a merge conflict, or a red check that `main` fixes (a pull request need not be up to date with `main`: pushes to `main` run the full CI); not while it waits on the product owner. A conflict in app code (as in step 2) gets a `code-reviewer` round on the merge commit.
- Red CI: fix the cause and push. A fourth round of CI fixes needs the product owner first. Read only the failing jobs (the check runs of the latest commit, not the job list with every step), and of each log only its end or a `grep` for the error; one subagent at most per round extracts what a log holds.
- Outside review: Copilot reviews each pull request once by itself; when it reports an error or stays silent, the workflow `fallback-review.yml` posts a review comment «Fallback review» from MiniMax once CI finished (#1007). Wait for one of the two after CI (a Copilot review that says it was unable to review, e.g. for quota, is not one: wait for the fallback; #1024 was merged 15 seconds before it) and treat it like a reviewer's report: check each finding, fix it (Workflow 6) or answer why it does not hold. The workflow sets the commit status «Outside review» on the head once one of the two came or it commented «No review: …» (#1121); the ruleset of `main` requires it, so neither a merge nor auto-merge goes ahead before it. After «No review: …», merge without a review and say so in the pull request. When the status has not come 15 minutes after CI finished, re-run the latest «Fallback review» run of the branch, which sets it without a second review; start the workflow by hand (`workflow_dispatch`, input `pr`, always a new review) only when the pull request has no review yet.
- Right before merging: read the check runs of the latest commit, the latest run of `main` (`CLAUDE.md`, "When to ask", depends on it) and the open findings again. Merge with a merge commit once CI is green, the outside review is answered and the pull request is mergeable, or turn on auto-merge (merge commit) once nothing but CI is left and the outside review is answered, so GitHub merges when the required checks pass; a brief that says to turn on auto-merge earlier does not change this order (#1411). When auto-merge still shows `blocked` 10 minutes after the last required status, with every required check green and the outside review answered (e.g. CodeQL's default setup, not a required check, did not run on the head), merge directly with a merge commit, never with an admin bypass: a required check still pending keeps it waiting. Name its CI screenshot comment, or that there is none, in the closing report.
- A change to a `workflow_run` workflow (`fallback-review.yml`, `pr-comments.yml`) runs in `main`'s version, so it first runs on the next pull request after the merge: name that pull request in the closing report and read its run.
- Never without the product owner: what `CLAUDE.md`, "When to ask", lists for pushes and merges (merging while a Blocker/Major is open includes the two kinds "Done means" lets a task finish with).

## After the merge

The push to `main` runs the full CI, every browser included; pull requests run the E2E tests in Chromium and the API driver only. A red run on `main` opens the issue «CI auf main ist rot» (job "Main status"). A coordinator that splits a request among workers gives each worker session one issue and reads the runs of `main` itself, so no worker waits for one before its next issue (#1411); otherwise, after the merge, arm one check-in about 45 minutes later (`send_later`) and read the run of `main` that contains the merge commit (still waiting or running: arm another check-in); when it is red, its failure is this task's, as a red check of the pull request was (one run may test several merges: the failing scenario and `git log` show whose). Fix it in a new pull request with `Fixes #<that issue>` from this branch restarted on `origin/main`, through this skill again; a failure that is not this merge's goes as a comment on the issue and under "Blocked on me".

Done when the pull request is merged and the run of `main` with its merge is green or its failure is handled as above, or the state is under "Blocked on me".
