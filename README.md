# Dwello - Swiss Property Management System

**Status:** In Development
**Version:** 0.1.0
**Architecture:** SvelteKit BFF + ElysiaJS Backend + PostgreSQL

---

## Overview

Dwello is a comprehensive web application for managing residential properties in Switzerland, specifically designed for property managers (Liegenschaftsverwalter). The system handles building management, tenant relationships, rental contracts, invoice management, and most importantly, complex utility cost statement generation (Nebenkostenabrechnungen) with Swiss legal compliance.

### Target Users
- Property managers managing 1-5 buildings with <50 apartments
- Single user initially (no multi-user support in MVP)

### Key Features
1. Building & Apartment Management
2. Tenant & Contract Management
3. Invoice Management with LLM-powered categorization
4. Utility Cost Statement Generation with complex prorating
5. Swiss QR-bill Generation
6. Multi-language Support (German, French, Italian, Romansh, English)

---

## Technology Stack

- **Frontend:** SvelteKit + TypeScript + TailwindCSS
- **Backend:** ElysiaJS on Bun + PostgreSQL + Drizzle ORM
- **Authentication:** BFF Pattern with OAuth 2.0 / SSO
- **LLM:** any OpenAI-compatible API, by default a self-hosted Ollama (`qwen2.5:3b`)
- **Deployment:** Docker Compose
- **Maps:** OpenStreetMap + Leaflet
- **Internationalization:** svelte-i18n

## Quick Start

### Prerequisites

- Node.js >= 20.0.0
- Bun >= 1.0.0 (for backend)
- PostgreSQL >= 15
- Docker & Docker Compose (optional, for containerized deployment)

### Installation

1. **Clone the repository**
   ```bash
   git clone <repository-url>
   cd dwello
   ```

2. **Install frontend dependencies**
   ```bash
   npm install
   ```

3. **Install backend dependencies**
   ```bash
   cd backend
   npm install
   cd ..
   ```

4. **Set up environment variables**
   ```bash
   cp .env.example .env.local
   # Edit .env.local with your configuration
   ```

5. **Start the development servers**

   **Frontend (SvelteKit):**
   ```bash
   npm run dev
   # Runs on http://localhost:3000
   ```

   **Backend (ElysiaJS):**
   ```bash
   cd backend
   bun run dev
   # Applies missing database migrations, then runs on http://localhost:3001
   ```

6. **Database and demo data**

   `bun run dev` (and the Docker image on start) applies the SQL files in `backend/migrations` that the
   database does not have yet; `schema_migrations` records what is applied. `0001_schema.sql` creates the
   schema, `0002_stammdaten.sql` the master data every database needs (cost categories, distribution keys,
   predefined heating profiles). Settings need no rows; their defaults are in `config.service.ts`.

   All commands run in `backend/` and use `DATABASE_URL` from `.env` / `.env.local` in the project root or in `backend/`
   (default `postgresql://dwello:dwello@localhost:5432/dwello`):

   | Command | What it does |
   |---|---|
   | `bun run db:migrate` | Applies the migrations the database does not have yet |
   | `bun run db:reset` | Drops the database and sets it up anew from the migrations, empty except master data. Local databases only (refuses any other host) |
   | `bun run db:demo` | Loads the demo data; loading it again adds nothing |
   | `bun run dev:demo` | Demo data, then `bun run dev` |

   Start with demo data on a fresh database:
   ```bash
   cd backend
   bun run db:reset && bun run dev:demo
   ```

   The demo data (`backend/demo/demo-data.sql`, `backend/src/db/demo-data.ts`) is for trying the app and showing
   it: three buildings (Zürich, Luzern, Interlaken) with 13 apartments, 9 tenants and their rental contracts,
   invoices of 2024 (one repair that is not passed on), a company with a QR-IBAN, and three statements of 2024
   generated by the app like any other: with line items, management fee and PDF, one sent with an additional
   payment (QR-bill in the PDF), one draft and one paid. Demo data never goes into a migration, so production
   starts without it. A demo statement that already exists is kept; delete it in the app to have it generated anew.

   A schema change is a new numbered SQL file (e.g. `0003_<what>.sql`), never an edit of an applied one. A database
   from before the October 2026 baseline is refused with a hint to `bun run db:reset`.

## Development

### Available Scripts

**Frontend** (project root):
- `npm run dev` - Start development server
- `npm run build` - Build for production
- `npm run preview` - Preview production build
- `npm run test` - Run unit tests (Vitest, watch mode)
- `npm run test:coverage` - Run all unit tests once, fails below the coverage floors
- `npm run test:e2e` - Run E2E tests (`-- --project=api` for the API driver only)
- `npm run test:e2e:ui` - Run E2E tests in the Playwright UI
- `npm run check` - Type check (svelte-check, also `tests/` and `*.config.ts`)
- `npm run type-check` - TypeScript type checking (tsc)
- `npm run lint` - Lint frontend and backend (fails on warnings)
- `npm run format` - Format code with Prettier

**Backend** (`backend/`):
- `bun run dev` - Apply missing migrations, start backend dev server (hot reload)
- `bun run dev:demo` - Load demo data, then `bun run dev`
- `bun run build` - Build backend
- `bun run start` - Start production server
- `bun run test` - Unit and PostgreSQL tests, fails if coverage drops
- `bun run test:pg` - PostgreSQL tests only
- `bun run type-check` - TypeScript type checking
- `bun run db:migrate` / `db:reset` / `db:demo` - Database and demo data, see Quick Start step 6
- `bun run e2e-db` - Set up the E2E database `dwello_e2e` anew (the E2E run does this itself)
- `bun run mail-catcher` - Local SMTP server that keeps sent e-mails (used by the E2E run)
- `bun run lint` / `bun run format` - ESLint / Prettier for the backend only
- `bun run db:studio` - Drizzle Studio, a browser view of the database
- `bun run db:generate` - Drizzle Kit drafts a migration from `src/db/schema.ts` into `backend/migrations`; check it and
  name it like the others (`000N_<what>.sql`) before committing
- `bun run db:push` - Drizzle Kit changes the database directly, without a migration; only for throwaway databases

## Testing

### Unit Tests (Vitest)
```bash
npm run test
```

### Backend Tests (bun)
```bash
cd backend && bun run test     # unit and PostgreSQL tests, fails if coverage drops (scripts/coverage-check.ts)
cd backend && bun run test:pg  # PostgreSQL tests only
```

The PostgreSQL tests (`*.pg.test.ts`) run against their own database `dwello_test`, recreated from
`backend/migrations` before every run; the development database is never touched. Override it with `TEST_DATABASE_URL`.

### E2E Tests (Playwright)
```bash
npm run test:e2e
```

The E2E run starts its own stack (backend on 3101, production build of the frontend on 3100) against its own database `dwello_e2e`,
recreated from `backend/migrations` before every run (`cd backend && bun run e2e-db`). The development
servers and database are never touched; only PostgreSQL on 5432 is required. Override the database with
`E2E_DATABASE_URL`.

### Coverage
```bash
npm run test:coverage          # frontend
cd backend && bun run test     # backend
```

### External LLM provider

By default invoices are categorized by the local Ollama and invoice data stays on the server. With an external provider (`LLM_BASE_URL`, `LLM_API_KEY`), the billing entity, description and amount of each invoice go to that provider, and a description may contain a tenant's name. The privacy statement then names the provider and its country from `LLM_PROVIDER` and `LLM_PROVIDER_COUNTRY`; the backend refuses to start without them. Only `localhost`, `127.0.0.1`, `[::1]` and the compose service `ollama` count as the operator's server; any other host counts as external, including `host.docker.internal`, LAN addresses and a self-hosted model on another server (e.g. `LLM_PROVIDER="eigener Server des Betreibers"`, `LLM_PROVIDER_COUNTRY=Schweiz`). With `LLM_ENABLED=false` nothing is sent and no provider is named.

Before switching, the operator (not Dwello) makes sure that, under the Swiss Data Protection Act (DSG):

- a data processing agreement with the provider exists (Art. 9 DSG), and the provider does not use the data for training;
- the provider's country has adequate data protection, or safeguards such as standard contractual clauses are in place (Art. 16 DSG); in the USA only providers certified under the Swiss-U.S. Data Privacy Framework count as adequate;
- data is kept no longer than needed (prefer providers with zero or short retention, and data centers in Switzerland or the EU).

This is a checklist, not legal advice.

**Upgrading from `OLLAMA_*` variables:** the LLM is now any OpenAI-compatible API. Rename `OLLAMA_API_URL` to `LLM_BASE_URL` and append `/v1` (`http://ollama:11434/v1`), `OLLAMA_MODEL` to `LLM_MODEL`. The default model is `qwen2.5:3b`; pull it (`docker exec dwello-ollama ollama pull qwen2.5:3b`) or set `LLM_MODEL` to the model you have. The old variables are ignored.
