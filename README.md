# Dwello - Swiss Property Management System

**Status:** In Development
**Version:** 0.1.0
**Architecture:** SvelteKit BFF + ElysiaJS Backend + PostgreSQL

---

## Overview

Dwello is a comprehensive web application for managing residential properties in Switzerland, specifically designed for private landlords who manage their own rented property (in the app: Liegenschaftsverwalter). The system handles building management, tenant relationships, rental contracts, invoice management, and most importantly, complex utility cost statement generation (Nebenkostenabrechnungen) with Swiss legal compliance.

### Target Users
- Private landlords with little experience who use Dwello a few times a year, with 1-5 buildings and fewer than 50 apartments
- Guidance, plain words and confirmations come before speed for experts; personas in `docs/design/personas/README.md`
- Single user initially (no multi-user support in MVP)

### Key Features
1. Building & Apartment Management
2. Tenant & Contract Management
3. Invoice Management with LLM-powered categorization
4. Utility Cost Statement Generation with complex prorating
5. Swiss QR-bill Generation
6. Statements and reminders for tenants in German, French, Italian and English; the app in German, French, Italian and English

---

## Technology Stack

- **Frontend:** SvelteKit + TypeScript + TailwindCSS
- **Backend:** ElysiaJS on Bun + PostgreSQL + Drizzle ORM
- **Authentication:** BFF Pattern with OAuth 2.0 / SSO
- **LLM:** any OpenAI-compatible API, by default a self-hosted Ollama (`qwen3-vl:8b-instruct`)
- **Deployment:** Docker Compose
- **Language:** UI in German (de-CH, default), French, Italian and English (Paraglide JS)

## Quick Start

### Prerequisites

- Node.js >= 20.0.0 (frontend runtime)
- Bun >= 1.4 (package manager; backend runtime; older versions misread `bun.lock`)
- PostgreSQL >= 15
- Docker & Docker Compose (optional, for containerized deployment)

### Installation

1. **Clone the repository**
   ```bash
   git clone <repository-url>
   cd dwello
   ```

2. **Install frontend dependencies**
   ```bash
   bun install
   ```

3. **Install backend dependencies**
   ```bash
   cd backend
   bun install
   cd ..
   ```

4. **Set up environment variables**
   ```bash
   cp .env.example .env.local
   # Edit .env.local with your configuration
   ```

5. **Start the development servers**

   **Frontend (SvelteKit):**
   ```bash
   bun run dev
   # Runs on http://localhost:3000
   ```

   **Backend (ElysiaJS):**
   ```bash
   cd backend
   bun run dev
   # Applies missing database migrations, then runs on http://localhost:3001
   ```

6. **Database and demo data**

   `bun run dev` (and the Docker image on start) applies the SQL files in `backend/migrations` that the
   database does not have yet; `schema_migrations` records what is applied. `0001_schema.sql` creates the
   schema, `0002_stammdaten.sql` the master data every database needs (cost categories, distribution keys,
   predefined heating profiles). Settings need no rows; their defaults are in `config.service.ts`.

   All commands run in `backend/` and use `DATABASE_URL` from `.env` / `.env.local` in the project root or in `backend/`
   (default `postgresql://dwello:dwello@localhost:5432/dwello`):

   | Command | What it does |
   |---|---|
   | `bun run db:migrate` | Applies the migrations the database does not have yet |
   | `bun run db:reset` | Drops the database and sets it up anew from the migrations, empty except master data. Local databases only (refuses any other host) |
   | `bun run db:demo` | Loads the demo data; loading it again adds nothing |
   | `bun run dev:demo` | Demo data, then `bun run dev` |

   Start with demo data on a fresh database:
   ```bash
   cd backend
   bun run db:reset && bun run dev:demo
   ```

   The demo data (`backend/demo/demo-data.sql`, `backend/src/db/demo-data.ts`) is for trying the app and showing
   it: three buildings (Zürich, Luzern, Interlaken) with 13 apartments, 9 tenants and their rental contracts,
   invoices of 2024 (one repair that is not passed on), a company with a QR-IBAN, and three statements of 2024
   generated by the app like any other: with line items, management fee and PDF, one sent with an additional
   payment (QR-bill in the PDF), one draft and one paid. Demo data never goes into a migration, so production
   starts without it. A demo statement that already exists is kept; delete it in the app to have it generated anew.

   A change to the schema or the master data is a new numbered SQL file (e.g. `0003_<what>.sql`), never an edit,
   rename or deletion of a migration on `main`: an installation has applied it and would not see the change. CI
   refuses a pull request that changes one. A database from before the October 2026 baseline is refused; set up a
   local one anew with `bun run db:reset`, never an installation (it deletes all records).

### Deep modules (deepcheck)

deepcheck finds shallow modules (A Philosophy of Software Design, ch. 4): an interface almost as large as what it hides.
It is a warning system, not a verdict on design quality.

When it runs:
- Before every `git commit` and `git push` (Claude Code hook) and in the CI job "Deep modules", on the changed modules only.
- A changed module fails when it is new or got shallower, scores at least 65 and contains a pass-through (a function
  that only forwards its parameters) or classitis (one module cut into tiny files). An exception comment without a
  reason fails too.

Commands (repo root):
- `bun run deepcheck:audit` - check the changed modules as the hook does; silent when clean
- `bun run deepcheck:scan` - list the flagged modules of the whole repo; `bun run deepcheck:scan -- --min-score 35`
  ranks every module scoring 35 or more, a review aid that never fails
- `bun run deepcheck:ci -- origin/main` - the CI check against a base branch
- `bun run deepcheck:baseline` - rewrite `.deepcheck-baseline.json` after a deliberate scoring change

When it reports a module:
1. Read the reason; `node tools/deepcheck/src/cli.ts --explain <path>` shows every metric.
2. Fix the design: merge forwarders into their callee, pull tiny files together, hide steps behind one function.
   Do not pad a module to lower its score.
3. For a deliberate exception put `// deepcheck-ignore-file -- <reason>` at the top of the file; it shows in review.

Metrics, weights, configuration and known false positives: [tools/deepcheck/README.md](tools/deepcheck/README.md).

## Testing

### Unit Tests (Vitest)
```bash
bun run test
```

### Backend Tests (bun)
```bash
cd backend && bun run test     # unit and PostgreSQL tests, fails if coverage drops (scripts/coverage-check.ts)
cd backend && bun run test:pg  # PostgreSQL tests only
```

The PostgreSQL tests (`*.pg.test.ts`) run against their own database `dwello_test`, recreated from
`backend/migrations` before every run; the development database is never touched. Override it with `TEST_DATABASE_URL`.

### E2E Tests (Playwright)
```bash
bun run test:e2e
```

The E2E run starts its own stack (backend on 3101, production build of the frontend on 3100) against its own database `dwello_e2e`,
recreated from `backend/migrations` before every run (`cd backend && bun run e2e-db`). The development
servers and database are never touched; only PostgreSQL on 5432 is required. Override the database with
`E2E_DATABASE_URL`.

### Coverage
```bash
bun run test:coverage          # frontend
cd backend && bun run test     # backend
```

## Deployment

### Docker Compose

**Development:**
```bash
docker-compose -f docker-compose.dev.yml up
```

**Production:**
```bash
APP_VERSION=$(git describe --tags --match 'v*') docker-compose -f docker-compose.prod.yml up --build
```

**First start (#577):** no `.env` is needed. The service `secrets` (`docker/init-secrets.sh`) makes the session key, the database password and the key for stored secrets once into the volume `dwello_secrets` (back it up with the database; values in `.env` win, so older installations keep theirs). While no Konto mit Passwort exists and no provider is configured, every visitor gets «Dwello einrichten» (`/setup`), which needs the Einrichtungscode from `docker logs dwello-backend` (made on each start; 5 wrong codes lock the setup for 15 minutes). The setup offers «Lokale KI auf diesem Server» or «Später entscheiden» (no KI until one is chosen under «Einstellungen» › «KI», #620), unless the operator set an `LLM_*` variable. The backend downloads the local KI's model on start when Ollama lacks it; the overview shows the progress, or, after «Später entscheiden», that no KI is chosen yet.

**Public demo** (demo.dwello.ch, shared data reset every night): [deploy/demo/README.md](./deploy/demo/README.md).

### Versions

Every merge to `main` gets the next version as a tag and a GitHub Release (`.github/workflows/release.yml`, `tools/release/`): a `feat` commit raises the minor version, anything else the patch version; a breaking change (`feat!:`, `BREAKING CHANGE:`) raises the minor version before 1.0 and the major version after. Merges that land while a release still runs share the next version. A manual run of the workflow on `main` sets a version by hand (e.g. 1.0.0, not one that exists already) in place of the one the last merge got. The footer shows the version the build was made from (`git describe --tags`, or `APP_VERSION` for a Docker build, which has no `.git`). The `version` field in `package.json` is not maintained.

### Environment Variables

See [.env.example](./.env.example) for the optional environment variables; an installation needs none (#577).

**Konto mit Passwort (#576):** the default sign-in. The landlord creates the account in the setup on the first visit (#577), or the Betreiber in the backend container with `docker exec -it dwello-backend bun run account` (e-mail address, password of at least 8 characters, stored only as Argon2id hash); the same command sets a forgotten password, lifts a Sperre (5 failed attempts lock sign-in for 15 minutes) and ends the open sessions of that account. The sign-in page offers the password form as soon as an account exists, and Google as soon as `OAUTH_GOOGLE_*` is set; both can be used side by side. See `docs/installation.md`.

**Who may sign in with Google:** `ALLOWED_EMAILS`, set for the frontend, lists the e-mail addresses that may sign in with a provider, separated by commas; spaces and case do not count. Only Google accounts whose address Google reports as verified are let in, and Microsoft accounts are refused while the list is set. `ALLOWED_EMAILS=*` lets every account in (the public demo). With `NODE_ENV=production`, a provider configured and no `ALLOWED_EMAILS` the frontend refuses to start; a Konto mit Passwort needs no list. An address removed from the list loses its open sessions in the app at its next request; the backend accepts its session token until it expires (`JWT_EXPIRY`), so a backend published on the host (see `docker-compose.prod.yml`) stays reachable with it until then. Changing `JWT_SECRET` ends every open session at once: everyone signs in again.

The terms of use name the operator of the installation (who runs it and backs up its data) from `OPERATOR_NAME`, `OPERATOR_ADDRESS` and `OPERATOR_CONTACT`, set for the frontend. Without `OPERATOR_NAME` they speak of "the operator" only.

The privacy statement names the country of the server from `OPERATOR_SERVER_COUNTRY`, and with `MAIL_TRANSPORT=smtp` the provider and country of the mail server from `MAIL_PROVIDER_NAME` and `MAIL_PROVIDER_COUNTRY` (both needed), all set for the frontend. They are required when the server or the mail server is outside Switzerland (Art. 19 para. 4 FADP); the values are shown as entered, in all four languages.

### External LLM provider

By default invoices are categorized by the local Ollama and invoice data stays on the server. The landlord chooses the KI in the browser under «Einstellungen» › «KI» (#580): the local KI, an external provider (address, API key, model, provider name and country) or none; the next invoice uses the new choice, without a restart. «Verbindung prüfen» sends a fixed test text and image (never recorded data) and says whether the key is accepted and the model reads images. The API key is stored only encrypted with the installation's key for stored secrets (`ENCRYPTION_KEY`, made by `docker/init-secrets.sh`) and never shown again; it is never sent to another address than the one it was saved for. Every change of the KI goes into the Protokoll under «Einstellungen» with provider and country.

With an external provider, the billing entity, description and amount of each invoice and the name and description of every category go to that provider, and so do the name and description of a new category the user lets the KI check (#176); a description may contain a tenant's name. An invoice file uploaded in «Rechnungen hochladen» goes to the provider as images of its pages, with its file name, as soon as it is added (#217): it contains everything printed on the invoice, names and addresses included. The privacy statement then names the provider and the country where the data is processed, whatever the address (also one in the own network); a provider cannot be saved without them and without the confirmed checklist below. With «Keine KI» nothing is sent, no provider is named, and the privacy statement says that no KI processes invoices or categories.

**Set by the operator:** any of `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `LLM_PROVIDER`, `LLM_PROVIDER_COUNTRY` or `LLM_ENABLED`, set and not empty, takes precedence over the choice in the browser and locks the page «KI» (it shows the values, never the key), as on the public demo. Then the privacy statement names the provider from `LLM_PROVIDER` and, from `LLM_PROVIDER_COUNTRY`, the country, and the backend refuses to start without them; only `localhost`, `127.0.0.1`, `[::1]` and the compose service `ollama` count as the operator's server, any other host counts as external, including `host.docker.internal`, LAN addresses and a self-hosted model on another server (e.g. `LLM_PROVIDER="eigener Server des Betreibers"`, `LLM_PROVIDER_COUNTRY=Schweiz`). With `LLM_ENABLED=false` no KI is used. `LLM_LOCAL_URL` only says where the local KI runs (`http://ollama:11434/v1` in `docker-compose.prod.yml`) and locks nothing; it must be on the server itself (one of the hosts above), or the backend refuses to start, because the privacy statement then says that invoices do not leave the server. A model on another machine is a provider.

Before choosing a provider, whoever sets the KI (the landlord on the page «KI», who confirms these three points there for each provider, or the operator in `.env`) makes sure that, under the Swiss Data Protection Act (DSG):

- a data processing agreement with the provider exists (Art. 9 DSG), the provider does not use the data for training, and it engages other companies only with consent;
- the data is processed only in Switzerland or in a country the Federal Council lists with adequate data protection (Art. 16 Abs. 1 DSG, DSV Anhang 1), data centers and subprocessors included, within the limits noted there (in the USA only providers certified under the Swiss-U.S. Data Privacy Framework); the country field names that country, or all of them when the data is processed in several. The privacy statement names only the provider and its country (Art. 19 Abs. 4 DSG); it cannot name safeguards under Art. 16 Abs. 2 DSG (e.g. standard contractual clauses) or an exception under Art. 17 DSG, so such providers are not supported (#184);
- data is kept no longer than needed (prefer providers with zero or short retention, and data centers in Switzerland or the EU).

This is a checklist, not legal advice.

**OpenRouter (optional):** reading uploaded invoices needs a model that reads images. Through OpenRouter, for example: address `https://openrouter.ai/api/v1`, your key, model `qwen/qwen3-vl-8b-instruct` (the default model), provider `OpenRouter`, country `USA` (in `.env`: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `LLM_PROVIDER`, `LLM_PROVIDER_COUNTRY`). Check the checklist above first: OpenRouter is based in the USA and passes each request on to a model provider of its own choice. Restrict the routing in the OpenRouter account to providers you have checked, and name all recipients with their countries as provider and country (e.g. «OpenRouter, Alibaba Cloud» and «USA, Singapur»), so the privacy statement names them (Art. 19 DSG).

**Upgrading from `OLLAMA_*` variables:** the LLM is now any OpenAI-compatible API. Rename `OLLAMA_API_URL` to `LLM_BASE_URL` and append `/v1` (`http://ollama:11434/v1`), `OLLAMA_MODEL` to `LLM_MODEL`. The default model is `qwen3-vl:8b-instruct` (Ollama 0.12.7 or later); the backend downloads it on start when Ollama lacks it (#577), or set `LLM_MODEL` to the model you have. The old variables are ignored.

**Upgrading from the default model `qwen2.5vl:7b`** (#419): an installation without `LLM_MODEL` now asks Ollama for `qwen3-vl:8b-instruct`. Update the Ollama image first (`docker compose -f docker-compose.prod.yml pull ollama`, then `up -d`), pull the model (command above), or keep the old model with `LLM_MODEL=qwen2.5vl:7b`; until one of them is done, the KI suggests nothing. Ollama's plain `qwen3-vl:8b` is the thinking variant, a different and slower model. Without a GPU (4 CPU cores) the new model needs about 40 s to categorize an invoice (the old one about 20 s) and about 80 s to read an uploaded file; `LLM_TIMEOUT` therefore defaults to 120000 ms.

**Upgrading from `BACKEND_API_URL`:** the frontend reads the backend address only from `BACKEND_URL` now. Rename the variable in your `.env`; `docker-compose.prod.yml` sets it already.
