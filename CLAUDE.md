# Dwello

Web app for Swiss private landlords who manage their own rented property (in the app the Liegenschaftsverwalter; target users in "Design-Regeln"): buildings, apartments, tenants, contracts, invoices categorized by an LLM, utility cost statements (Nebenkostenabrechnungen) with Swiss QR-bills. Single-user MVP, under 50 apartments.

Stack: SvelteKit + TypeScript + Tailwind (frontend and BFF) | ElysiaJS on Bun + Drizzle + PostgreSQL (`backend/`) | an LLM for invoice categorization (any OpenAI-compatible API, by default a local Ollama).

## Commands

Frontend (repo root):

```bash
bun run dev                         # dev server; needs the backend running
bunx vitest run                      # all unit tests once (bun run test starts watch mode)
bunx vitest run src/__tests__/x.test.ts   # one file; *.dom.test.ts run in jsdom (mounting, clicking), all others in node
bun run test:coverage               # with coverage floor, as in CI
bun run lint                        # ESLint, fails on warnings
bun run check                       # svelte-check incl. tests/ and *.config.ts
bun run test:e2e                    # acceptance tests, see tests/e2e/CLAUDE.md (test:e2e:wip for @wip)
```

Backend (`cd backend`): see `backend/CLAUDE.md`. Short form: `bun run dev:demo` (app with demo data), `bun run test`, `bun test src/__tests__/x.pg.test.ts` (one file), `bun run type-check`.

PostgreSQL on localhost:5432 (user and password `dwello`) is required for backend tests and E2E. The test databases `dwello_test` and `dwello_e2e` are recreated automatically; the development database `dwello` stays untouched through the test preload, which `backend/bunfig.toml` sets for every `bun test` started in `backend/` itself (Bun reads `bunfig.toml` only from the working directory).

## Architecture (BFF)

`Browser -> apiCall() (src/lib/api.ts) -> SvelteKit BFF (src/routes/api, src/routes/auth, src/lib/server) -> Elysia (backend/src/routes -> services) -> PostgreSQL`

- The BFF does OAuth, keeps the session JWT in HTTPOnly cookies and checks the XSRF token; the client never sees a token.
- The backend validates the JWT from the `Authorization` header and holds all business logic in `backend/src/services`.
- Pages load data in `+page.server.ts`; mapping and form handling live in `src/lib/server/*.ts`.

## Conventions

- **Language:** UI texts, Gherkin scenarios and test names in German (Swiss spelling, "ss" instead of "ß"); code, comments, commits and PR descriptions in English.
- **UI languages:** every UI text lives in `messages/{de,fr,it,en}.json` (Paraglide JS; German is the base and default, terms per language in `docs/design/i18n-begriffe.md`) and is shown with `m.key()` from `$lib/paraglide/messages`; never call a message at module level in server code (use a getter or function). `bun run i18n` regenerates `src/lib/paraglide/` (not committed). Every new or changed text goes into all four files in the same change: formal address (Sie, vous, Lei), verbs on buttons, Swiss terms; an unsure term gets an issue (labels `fachlich`, `entscheiden`; see "Open work"). A backend refusal the UI shows carries a code (`backend/src/services/coded-error.ts`) and a message `backend_<code>`, shown with `backendMessage()` from `$lib/backend-error`; never the backend's own text.
- **Domain terms:** use the words from `UBIQUITOUS_LANGUAGE.md` in code and scenarios.
- **Selectors:** `data-testid` in kebab-case with component context (`building-card-{id}`, `tenant-name-input`); no CSS selectors in tests.
- **No mock data in the app:** components and pages always use the real backend and database. Test doubles in tests follow `docs/test-pyramid.md`.
- **Commits:** Conventional Commits `<type>(<scope>): <subject>`, at most 50 characters, imperative, no period. Types: `feat`, `fix`, `docs`, `chore`. Scopes: `auth`, `buildings`, `apartments`, `tenants`, `contracts`, `invoices`, `statements`, `config`, `components`, `stores`, `styles`, `api`, `db`, `middleware`, `services`, `schema`, `docker`, `types`, `i18n`, `tests`, `ci`, `build`.

## Design-Regeln

- **Target users:** private landlords with little experience who use Dwello a few times a year. Prefer guidance, plain words and confirmations over speed for experts.
- **Copy:** German, formal "Sie", Swiss "ss", short sentences, verbs on buttons; errors say what happened and what to do. Domain terms only from `UBIQUITOUS_LANGUAGE.md` (never edit it); missing terms get `TODO(fachlich prüfen, #<issue>)` and an issue (see "Open work"). Explain terms with visible help text at the field, not tooltips.
- **Tokens are mandatory:** only the token classes from `docs/design/token-referenz.md` (`bg-surface`, `text-ink`, `border-line-strong`, `rounded-control`, `shadow-raised`, 8 px grid …) and the components in `src/lib/ui`. No raw colours, no arbitrary values (`w-[…]`), no `text-xs`, no other radii or shadows; dark mode comes from the tokens. `src/__tests__/design-guard.test.ts` and `tokens.test.ts` enforce this.
- **Screens:** one primary action per screen, at most two navigation levels, controls at least 48 px high, labels above fields, list rows whose whole area is one link named by the record, no sideways scrolling at 390 px. Irreversible actions confirm with their real consequence.
- **Anti-patterns:** gradients, glow, blur/glassmorphism, emoji as icons, shadow cards everywhere, decoration without function, external fonts or icon fonts, lorem ipsum, colour as the only carrier of information.
- **Process:** every UI change loads the skills `tdd` (a failing test first) and `ponytail` (Workflow 2 and 3; following their rules without loading them is not enough); new screens or states go into `tests/a11y/screens.json`, `accessibility.feature` and `sprachen-bildschirme.feature`, one entry per place a state appears (each page, each wizard step: axe checks the page around it); axe in light and dark, desktop, tablet and mobile, 0 violations, no rule exceptions, no German in fr/it/en; reviews as in "Workflow", steps 4 to 7. Decisions and history: `docs/design/design-decisions.md`, `docs/archive/redesign/progress.md`.

## Workflow

1. **Acceptance test first (ATDD):** every feature or behavior change, including a bug fix a user can see, starts with a German scenario in `tests/e2e/features/*.feature`, tagged `@wip` (excluded from runs). Watch it fail for the right reason and note the failing line in the plan checklist (`Scenario red: <assertion>`). A state that only a failing request reaches gets its scenario too, with that endpoint (all its calls) answered with an error status only, at the browser boundary (`docs/test-pyramid.md`); this works only for requests the browser makes, so a scenario cannot be `@api`, and a failure only between server parts (a load function, the BFF calling the backend) gets a lower-layer test and `No scenario: server-side failure` instead.
   If the change touches domain rules, amounts, PDFs or domain terms: before implementing, commit the `@wip` scenario locally and give subagent `fach-reviewer` a worktree of that commit (step 4); it checks the scenario against `UBIQUITOUS_LANGUAGE.md`, `docs/nebenkostenabrechnung-anforderungen.md`, `docs/anforderungen-vertragsende.md` and the law on Fedlex (quoted verbatim). Until it reports back, write at most the first lower-layer test and watch it fail: no production code, no texts in `messages/*.json`. Fix its findings before the first test turns green.
2. **`/tdd`:** load the skill `tdd` before writing the first test of a slice, then drive the implementation red-green, one behavior at a time, through public interfaces. A test must fail before the code changes; note it in the plan like the scenario (`Test red: <test> – <message>`). If a test was nevertheless written after the code, show its red by taking the code out again. Every bug fix also gets a test that reproduces it first, at the lowest layer that can show it (unit, DOM or `*.pg.test.ts`), in addition to the scenario of step 1.
3. **`/ponytail`:** keep the shortest diff that works (load the skill `ponytail` before writing code); before the review of a slice that changes code, apply the skill `ponytail-review` to its diff and note in the plan which skills ran (`Skills: tdd, ponytail, ponytail-review`).
   **Deep modules:** after each implementation step run `bun run deepcheck:audit` (silent when clean) and fix its findings before continuing; run `bun run deepcheck:scan` only when a codebase-wide review is requested (`tools/deepcheck/README.md`).
4. **Slice review:** after each slice (a green scenario or a coherent group of behaviors), once lint, the affected tests and `deepcheck:audit` are clean, commit it locally and run subagent `code-reviewer` (fresh context: requirement + commit range, plus the results of the checks you ran: at least lint, the affected tests and `deepcheck:audit`; coverage, check and scenarios when run). Give every reviewer subagent (`code-reviewer`, `fach-reviewer`, `daten-pruefer`) its own worktree of the reviewed commit and name it in its prompt (`git worktree add --detach <scratchpad>/review-<slice>-<reviewer> <commit>`, then link `node_modules` and `backend/node_modules` into it) and a report path in your scratchpad, which you copy to its place under step 6; then keep working in your tree, but do not amend or rebase the reviewed commits while it runs. Remove the worktree after the triage (`git worktree remove`). Triage its findings (step 6). Continue only when no Blocker/Major is open (limit: step 7).
5. **Feature review:** when the scenario is green, start the app once with `docs/design/tools/persona-stack.sh`, then run in parallel, only where it applies, telling each subagent the app is running:
   - UI changed: subagent `persona`, once per affected persona (`docs/design/personas/README.md`, "Which personas": by screen, device and kind of change; when unsure, all), each with a task on the change instead of its default task. For a state reached only by a failure (a request that fails, a slow connection), name the request to fail; the persona simulates it.
   - Domain rules or terms changed: `fach-reviewer`.
   - Amounts, statements, PDFs or QR-bills changed: `daten-pruefer`.
   Personas that run at the same time share one database: give each persona that needs to save its own building of the demo data, as long as buildings are left, and say in its task that saving in the persona app is part of it (`dwello_persona` is recreated for each run); the others only look. Name records only from `docs/design/personas/demo-records.md`. Personas use the app's copy of the build, not your tree: keep working while they run, but run no E2E (Gotchas, "One build").
   If you cannot start subagents, do not skip the reviews: list the missing ones under "Blocked on me".
6. **Findings:** every reviewer reports severity (Blocker / Major / Minor / Nit) plus evidence (file:line or reproduction steps) and writes its report itself to the path you name: `docs/reviews/<slice>-review-<n>.md`, `<slice>-fachreview-<n>.md` or `<slice>-datenpruefung-<n>.md` (personas to `docs/design/personas/<persona>-<slice>.md`); the latest `## Session` of `implementation_plan.md` gets one line per reviewer and round: `<reviewer> round <n> (<report path>): open <ID (severity)>, fixed <IDs>, rejected <ID: reason>`; the findings themselves stay in the report. A finding fixed in a later round changes its status in the line of the round that raised it. Check a finding's evidence before acting on it; reject it with a reason when it does not hold. A fix that changes behavior (a changed help or error text the user sees included) gets a failing test first. Re-review only the delta and the open findings. A fixed persona finding is closed by a test that shows it (scenario or lower layer, red before the fix); the persona runs again only when the fix adds a text or screen state it has not seen. Findings still open when the task ends become open work (see "Open work").
7. **Done:** remove `@wip` once the scenario is green. A feature is done when its scenario passes, not when unit tests pass, and when no Blocker/Major from `code-reviewer`, personas, `fach-reviewer` or `daten-pruefer` is open, except two kinds that become open work (see "Open work") and go under "Blocked on me": one that needs a product decision (it contradicts what the issue decided; an `entscheiden` issue), and one that existed before the change (it shows on the base commit too). Minors/Nits left unfixed become open work. A round is one run of one reviewer on one slice: if the same reviewer still reports an open Blocker/Major on the same slice after its 3rd round, stop, list the open findings under "Blocked on me", ask me. If after its 3rd round it reports only Minors/Nits of a kind it found before (another bypass of the same rule, another wording of the same gap), record the kind once as open work and end the review of that slice.
8. **Plan:** at the start of a task, first move a finished earlier session (every item ticked) to `docs/archive/implementation-plan-verlauf.md` (`open-work.test.ts` allows one session), then add the new task's items as a checklist to the latest `## Session` of `implementation_plan.md` (a new session for a new task); tick each item when done, add anything new you find, note the files changed. When the task is done, move its session to `docs/archive/implementation-plan-verlauf.md` before the final commit.

Keep going without asking while no input is needed; put status notes in the same message as your next action. Ask only when blocked, before anything destructive (deleting data, force-push, changes outside this repo), or where a rule here says to ask (conflicting instructions that drop a finish-line item, work outside the request). Commit locally per slice and push nothing before the task is done. When it is done (Workflow 7, every check under "Before marking anything complete" passes), the session that holds my task (not a subagent or a session it started) pushes the branch, opens a pull request (English, `Fixes #n` for the issue it finishes, the CI screenshot comment named in the closing report) and follows it until it is merged (subscribed to its activity where the session can, otherwise checking it before it stops): on a merge conflict merge `origin/main` into the branch (no rebase, no force-push), on red CI fix the cause; before each such push run the checks of "Before marking anything complete" again, and a conflict in app code or a fix that changes code gets a `code-reviewer` round first (Workflow 4). Once CI is green on the latest commit and the pull request is mergeable, merge it yourself (merge commit; the repository has no auto-merge). Still only with my approval: a push or pull request in a task where I said to only commit, a push to `main`, a force-push, merging with a red check (one also red on `main` included), a fourth round of CI fixes, and merging while a finding is listed under "Blocked on me" (Workflow 7). When a push, pull request or merge waits for my approval or a decision, say so once under "Blocked on me" and stop, without asking again. A stop hook outside this repo (`~/.claude/stop-hook-git-check.sh`) may ask to commit, amend or push earlier: it does not override Workflow 4 or this rule. Not destructive: recreating the databases `dwello_persona`, `dwello_test` and `dwello_e2e`, and files in the scratchpad.

End every run with three headings: **Blocked on me** (decisions, open Blocker/Major, new issues and rows in `docs/design/offene-punkte.md`), **Changed** (files, commits), **Found** (findings by ID and status, issues closed and opened, what could not be confirmed).

Before marking anything complete, all of these pass: `bun run test:coverage`, `bun run lint`, `bun run check`, `cd backend && bun run test && bun run type-check`, and the affected E2E scenarios.

## Open work

- **Functional points** (domain, features, bugs) are GitHub issues in `rudini/Dwello`, one finishable task each, written with a template from `.github/ISSUE_TEMPLATE/`: topic label `fachlich`, `produkt` or `bug` (`betrieb` only on #51, written before this rule), plus `entscheiden` while a product-owner decision is missing. **Non-functional points** (security, operations, reliability, performance, usability and accessibility, maintainability) stay in `docs/design/offene-punkte.md` until the quality requirements are set up. There is no other list.
- A point you find but do not fix becomes an issue (or, if non-functional, a row in `offene-punkte.md`) in the same task. Before opening an issue, search the open issues for the same point (`search_issues`) and add to that one instead of opening a duplicate. A code marker names its issue: `TODO(fachlich prüfen, #42)`; find an issue's markers with `grep -rn "#42" src backend tests` (line numbers in issues drift). `src/__tests__/open-work.test.ts` checks markers in code, tests, migrations and demo data, not in prose docs; CI (`tools/open-work/check-issues.mjs`) checks that they name open issues, that a PR does not close an issue a marker still names, that an open issue with «Proposed (confirm before starting)» has the label `entscheiden`, and that a PR closing an issue with app changes also changes a scenario (or says `No scenario: <reason>` in its text).
- An issue is ready when its decisions are in its text. For an `entscheiden` issue: ask, do not start. When the product owner confirms a section "Proposed (confirm before starting)", rename it "Decided (product owner)" and remove the label. A decision issue (template "Decision") is closed once the decision is recorded in it and, if code must change, its implementation issue exists.
- Working on an issue ("Setze #n um"): its "Done means" plus this workflow is the finish line; its bullets become the checklist in `implementation_plan.md` and the scenarios of step 1. The commit or PR says `Fixes #n`; the issue closes on merge.
- Read and write issues with the GitHub MCP tools; in cloud sessions `gh issue view` can fail, `gh api repos/rudini/Dwello/issues/<n>` works.

## Gotchas

- **Never `bun test` in the repo root:** Bun is the package manager everywhere, but the frontend runs on Node. There `bun test` starts Bun's own test runner instead of Vitest, without `vitest.config.ts` (no jsdom, no coverage floor). Use `bunx vitest run`.
- **Fallow gate:** a hook runs `fallow audit` before every `git commit` and `git push` and blocks the whole Bash command on new unused exports or files, duplication, or complexity/CRAP findings. Run git commands on their own, not chained after edits, and fix the reported finding (un-export, delete, split the function) rather than working around it. `bunx fallow audit` shows the findings before committing (when it finds no base branch, as in a single-branch clone, the gate blocks: `git fetch origin main:refs/remotes/origin/main` fixes it); CI runs the same audit.
- **Deepcheck gate:** a second hook (`.claude/hooks/deepcheck-gate.sh`) runs the changed-scope deepcheck before every `git commit` and `git push` and blocks new or worsened shallow modules (pass-through layers, thin facades); CI runs the same check (job "Deep modules"). Fix the design, not the numbers; a deliberate exception needs `// deepcheck-ignore-file -- reason`.
- **Commit subject gate:** a third hook (`.claude/hooks/commit-msg-gate.mjs`) blocks `git commit -m` with a subject that breaks "Conventions" (type and scope from the lists there, at most 50 characters, no period).
- **One build:** `bun run test:e2e` and `docs/design/tools/persona-stack.sh` both build the frontend into `build/`; the E2E servers load their pages from there, the persona app from its copy in `/tmp/persona-app`. A persona stack started during an E2E run breaks that run, and both compete for the machine. Run E2E before starting the persona stack or after the personas are done.
- **API contracts:** a frontend test that reads a backend response takes it from `tests/contracts/*.json`, also when the response itself is unchanged (add a contract when there is none); `backend/src/__tests__/api-contracts.pg.test.ts` checks them against the real API. Changing an API response means updating its contract.
- **Coverage floors** in `vitest.config.ts` and `backend/scripts/coverage-check.ts` may not drop; the target is in `docs/test-pyramid.md`.
- **Formatting:** run Prettier only on files you create or change, never on a directory: many files are not Prettier-clean, and reformatting them is a change outside the task.
- **Branches:** work only on a named branch, never commit on a detached HEAD (a review worktree that is only read may be detached) (`git worktree add -b <branch> …`, `git switch -c`): a commit on no branch is lost at the next cleanup. One branch, one session: a session or subagent you start that commits gets its own branch and never pushes to yours (review subagents read their own worktree), and you never push to another session's branch. At the start of a task, `git fetch origin main` (`session-start.sh` reports a branch behind it): if the branch's pull request is merged, start the branch anew from `origin/main` before the first change (ask before the force-push this needs once the old branch was pushed); if it is only behind, merge `origin/main` first. After merging a newer `main` with conflicts in app code, run `code-reviewer` on the merge commit.
- **Cloud sessions:** `.claude/hooks/session-start.sh` installs dependencies, starts PostgreSQL with the role `dwello` and, when the project's Playwright expects another Chromium build than the image has, sets `PLAYWRIGHT_BROWSERS_PATH` to a shim. If E2E cannot start a browser or reach the database, run it again.
- **Web search:** use `mmx search "<query>"` (MiniMax CLI, add `--output json` for parsing; at most 10 results, no paging) for current library docs, Swiss legal or tax rules and error messages. In cloud sessions the real key is a network secret for `api.minimax.io`; the environment's setup script installs the CLI and stores a placeholder key (`npm install -g mmx-cli && mmx config set --key api_key --value placeholder`), because mmx refuses to run without a local key.

## Coding guidelines

- **Before coding:** state assumptions; if a request has several readings, name them instead of picking silently; when two instructions (this file, an issue, a template) disagree, say which you follow and why before starting, and ask before starting if following one drops a finish-line item (a scenario, a review); push back when a simpler approach exists.
- **Stay in scope:** do what the request names; work outside it (porting to another branch, fixing an area the request does not name) needs a short question first, or becomes open work.
- **One mapper per response:** a backend response used by several loads gets one mapper in `src/lib/server/<area>.ts`; reuse it instead of copying its fields or passing the response on untyped.
- **Surgical changes:** touch only what the task needs; match the surrounding style; don't reformat or refactor adjacent code. Remove what your change made unused, leave pre-existing dead code unless asked.
